# 웹 읽기 독립 실험 결과 (2026-10-26)

실험 Worker: https://daiso-web-read-lab.hmmhmmhm.workers.dev/run/round2

가상 상품과 수량만 사용합니다. 실제 상품 API, 인증, 중계는 호출하지 않습니다. 이 결과는 해당 실행의 관측이며 모든 ChatGPT 계정이나 도구 버전의 영구 규격을 뜻하지 않습니다.

## 결과

| 조건                                           | 관측                                                                          |
| ---------------------------------------------- | ----------------------------------------------------------------------------- |
| 새 URL을 web.run open에 직접 전달              | 16조건 모두 접근 오류, 해당 실험 번호 Worker 도착 기록0                       |
| 읽힌 GitHub PR의 링크를 web.run click으로 선택 | 실험 목록과 루트 정상, ChatGPT-User 분류 요청 도착                            |
| 목록의 HTML/text/JSON 링크 click               | 모두 실제 데이터 반환. requestId가 서버 기록과 일치                           |
| ASCII·한글 경로, ASCII·한글 쿼리               | click으로 모두 성공                                                           |
| 302리다이렉트                                  | 목적지 HTML 반환 및 서버 재요청 확인                                          |
| 고정1초 지연                                   | 성공                                                                          |
| 고정5초·15초 지연                              | TimeoutError. 서버 received는 있고 prepared는 없었음                          |
| 64KiB·256KiB HTML                              | 페이지와 앞부분 데이터 열람 성공. 전체 본문 보존을 검증한 것은 아님           |
| no-store / public,max-age=300 / noindex        | click으로 모두 성공                                                           |
| JavaScript만으로 데이터 표시                   | 페이지는 열리지만 웹 읽기 결과에 상품 데이터 없음. Work 브라우저에서는 표시됨 |
| no-store HTML 재열람                           | 이전 requestId·생성 시각 재사용, 새 서버 기록 없음                            |

일반 HTTPS 대조군16조건은 모두 기대한200/302였고 지연 응답은 약1.29/5.31/15.54초였습니다. 짧은 HTML은427바이트, 약0.53초였으며 Work 브라우저도 정상으로 열었습니다.

## 핵심 재현 순서

1. GitHub [PR329](https://github.com/hmmhmmhm/daiso-mcp/pull/329)를 URL 열기로 읽습니다.
2. 본문 실험 링크를 도구가 반환한 링크 ID로 click합니다.
3. 실험 목록의 html/json/한글 경로 링크를 click합니다. 새 URL 문자열을 임의로 open하는 시도와 구분합니다.
4. 응답의 requestId와 `/observations/{실험번호}`의 기록을 비교합니다.
5. 같은 HTML을 다시 읽고 번호·생성 시각·신규 서버 기록이 바뀌었는지 확인합니다.

첫 실행번호 a-6aa69ea371/b-ec18b14f0e의 직접 open에서는 도착 기록이 없었습니다. 링크 경유 start 실행에서는 응답 번호가 서버 기록과 일치했습니다. html은 직접 open 실패 후 click 성공, 이후 직접 open에서도 이전 사본이 반환되는 변화를 보였습니다. 따라서 단순한 JSON 미지원이나 한글 URL 문제로 설명할 수 없습니다.

## 해석과 한계

- 직접 URL 열기와 이미 읽힌 페이지의 링크 선택은 이 실행에서 서로 다른 결과를 보였습니다. 도구 내부 URL 처리·검색 사본 경로 차이를 의심할 수 있지만 내부 구현은 확인할 수 없습니다.
- 링크 click은 새 페이지를 실제 가져오기도 했으므로 모든 성공을 과거 검색 캐시라고 볼 수 없습니다. 반대로 재열람은 no-store여도 도구가 이전 결과를 재사용했습니다. no-store만으로 실시간 재조회를 보장할 수 없습니다.
- 지연 실험은1초 성공/5초 실패 사이의 제한을 시사합니다. 네트워크와 기록 비용이 포함되므로 정확한 타임아웃 초수로 일반화하지 않습니다. received만 남은 경우 서버 도착은 확인되지만 Worker 취소 사유는 이것만으로 확정하지 않습니다.
- 이 실험은 Cloudflare 앞단 기록 전체를 보지 않습니다. 도착 기록0만으로 WAF 차단과 도구 내부 거절을 구분할 수는 없습니다. 같은 호스트에서 click이 실제 도달한 점은 전면적인 호스트 차단 주장과 맞지 않습니다.
- 현재 에이전트 안내에는 실제 링크 ID로 click하는 방법을 구체적으로 명시할 가치가 있습니다. 느린 원본 조회는 별도 시간 측정이 필요하며 이번 실험만으로 운영 API의 타임아웃 원인을 단정하지 않습니다.
