# 웹 읽기 재시도와 접수형 조회 실험

2026년11월2일 실제 ChatGPT 웹의 새 임시 채팅에서 비교했다. 고정 가상 데이터를 쓰는 별도 Worker와 실제 운영 조회를 구분했다. 임시 채팅 UI와 개인화 제외 선택을 확인했으며, 답변의 자기보고만으로 실행 성공을 판정하지 않았다. 가상 실험은 서버 requestId·jobId·resultId와 received/prepared 기록을 대조했다. 이번 실험의 원시 웹 도구 인자나 내부 캐시 설정을 확보한 것은 아니다.

## 결론

**첫 실패 뒤 같은 URL을 재시도하면 성공할 것이라고 가정할 수 없다.** 완료 결과를 서버에 저장해도 동일 주소 재시도가 실패했다. 반면 즉시 접수하고 응답마다 새 실제 결과 링크를 제공하면 완료 결과를 읽는 사례를 확보했다.

| 조건 | 관측 |
| --- | --- |
| 매번5초 지연, 저장 없음 | 첫 요청과 같은 주소 재시도 모두 시간 초과 |
| 첫5초 뒤 완료 결과 저장 | 같은 주소 재시도는 시간 초과 유지. 서버 알람으로 저장된 결과는 별도 결과 URL에서 읽힘 |
| 즉시 접수, 같은 결과 링크 반복 | 첫 pending을 반복해서 읽음. 답변은 두 번 재확인했다고 했지만 관측된 결과 주소 도착은 한 번 |
| 즉시 접수, 응답마다 새 실제 결과 링크 | 독립 임시 채팅 두 건 모두 최대3회 링크 선택 안에 ready와 가상 수량7 확인. 서로 다른 요청 ID와 같은 작업 ID를 서버 기록으로 대조 |
| 운영 다이소 읽기 세션 | pending 뒤 후속 링크 한 번으로 success:true. 같은 결과 주소를 별도 HTTPS로 확인해 읽기 ID·본문·완료 시각 일치 확인 |

같은 주소 재시도에서 새 서버 도착이 확인되지 않고 실패나 pending이 유지되는 현상은 웹 도구의 사본 재사용 또는 참조 처리 차이와 양립한다. 내부 캐시 정책이나 모든 계정의 동작으로 단정하지 않는다. HTML의 no-store만으로 사본 재사용을 막는다고 보장할 수 없다. 접수 응답에서 URL이 보이지 않아 후속으로 진행하지 못한 표본도 있었으며, 실제 href와 완성 URL을 함께 제공하도록 보강했다.

브라우저 편집기 포커스·페이지 준비·제어 컨텍스트 문제로 전송 전 중단된 시도는 웹 조회 실패 표본에 포함하지 않았다. 소유 창과 탭만 순차 사용하고 finally에서 캡처와 세션을 회수했다.

## 운영 반영

[PR347](https://github.com/hmmhmmhm/daiso-mcp/pull/347)은 격리된 가상 작업을 추가했고, [PR349](https://github.com/hmmhmmhm/daiso-mcp/pull/349)는 새 결과 링크와 완성 URL을 추가했다. [PR348](https://github.com/hmmhmmhm/daiso-mcp/pull/348)은 사용자 복사 재전송 문구와 문서의 실제 링크 우선 규칙을 통일했다.

[PR350](https://github.com/hmmhmmhm/daiso-mcp/pull/350)은 우선 다이소 `/browse/read` 조회에 접수형 처리를 적용했다.1초 안에 끝나면 기존 결과를 반환하고, 느린 경우 접수 HTML과 새로운 결과 확인 링크를 반환한다. 상태 확인은 저장 결과만 읽으며 원본 API를 재호출하지 않는다. 원본의 IP·권한·한도·캐시와 오류 상태를 유지한다.25초 작업 제한,5분 조회 수명,256KiB 저장 상한을 적용한다. 요청 헤더·토큰·쿠키는 저장하지 않는다. 연결 종료 전부터 수명을 보호하고 다이소 HTTP 호출의 취소를 전달한다. 완료와 알람의 경합도 검증했다.

현재 안내는 `/guide/latest`에서 확인한다. 사용자가 복사할 문장은 에이전트가 완성 URL로 채워서 제공해야 한다. 직접 URL 조합을 반복하는 대신 [접근 오류 진단](web-reading-troubleshooting.md)의 복구 절차를 따른다. 접수형 처리가 URL 출처에 따른 접근 제한 자체를 해제하는 것은 아니다.

- [다이소 범위 운영 스모크41379968241](https://github.com/hmmhmmhm/daiso-mcp/actions/runs/41379968241)은 CLI5명령과 공개 MCP10도구·상품명 기반 재고 조회를 통과했다. 로컬 자원 보호가 브라우저 수로 거절한 검사를 우회하지 않고 임시 클라우드 검사 분기를 사용했다. 그 분기는 검사 후 삭제했으며 main의 전체12서비스 야간 검사 목록은 유지했다.
- 운영 API 캐시를 우회한 실시간 수량 보장이나 모든 ChatGPT 계정에서의 보편적 성공을 주장하지 않는다. JSON API·CLI·MCP 연결과 REST HTML 조회는 별개다. 다른 서비스는 기존 조회 경로를 유지한다.


## 첫 사용 시간 개선과 실제 Chat 재검증

[PR359](https://github.com/hmmhmmhm/daiso-mcp/pull/359)은 검색어와 지역을 통째로 선택하는 실제 링크를 추가했다.
일반 상품 검색어32개와 지역32개를 제공하며 목록 밖 입력의 기존 글자 선택은 보존한다.
새 진입점은 `/browse/quick`이며 최신 안내 버전은2026-11-02.3이다.
상품 결과의 매장 지역 선택을 바로 사용해 불필요한 상세 조회를 생략한다.
정상적인 빠른 경로는 시작·상품·지역 선택·재고4페이지다. 느린 원본 조회의 pending 결과 페이지는 추가될 수 있다.

기존 글자 입력은 한글 한 글자에 초성·중성·완성 선택이 필요했다.
지갑과 강남역의 다섯 글자만으로 입력 단계15회가 생긴다.
이전 실험의 상품 HTML과 재고 HTML 사이에는64.011초 차이가 있었다.
이후 일반 HTTP 비교에서는 상품1.500초, 재고2.077초였으므로 반복 웹 읽기와 판단이 조사 대상이다.
후속 측정만으로 이전 요청 당시의 서버 지연이나64초 전체의 원인을 확정하지 않는다.

새 ChatGPT 임시 대화를 순차 실행한 결과는 다음과 같다.
첫 질문에 개별 상품·재고 URL이나 상품 ID를 미리 제공하지 않았다.

시간은 응답 완료를 관측할 때까지다. 전송 후 관측은5초 주기 UI 읽기와 도구 비용을 포함한다.
새 표본은 결과 링크 href 회수를 완료한 시간이 아니라 응답 관측 시점을 사용했다.
빠른 진입 질문은 기존 루트 질문의 시작 주소만 `/browse/quick`으로 바꿨다.
이전과 비교해 준비 포함 관측은 약147초에서70초로 줄었지만, 서로 다른 진입점이며 모델·캐시·브라우저 상태가 통제되지 않았다.
이 값을 모든 첫 사용자에 대한 보장이나 순수 서버 속도 개선율로 제시하지 않는다.

빠른 진입 표본은 새 읽기 세션의 상품·지역 선택·재고 href를 표시했다.
상품 HTML13:59:55 KST, 재고 HTML13:59:57 KST이며 안내2026-11-02.3을 확인했다.
실제 첫 상품1057565의 강남역점16개·강남역2호점8개를 표시했다.
후속 일반 JSON 조회에서도 같은 ID와 매장별 수량, unknownStockCount0을 확인했다.
온라인 수량180은 매장별 수량과 별개다. 이 대조는 캐시 우회나 원본 갱신 시각 검증이 아니다.
pending은 발생하지 않았으므로 이번 표본으로 접수형 경로 활성화를 주장하지 않는다.

자연어 발견 두 표본은 실패했다. 오류 원문·raw 웹 도구 인자를 수집하지 않아 서버 장애나 DNS 오류로 확정하지 않는다.
공식 루트 표본은 이전 읽기 ID의 상품 HTML을 재사용한 뒤 최신 안내를 확인했다.
따라서 최신 문서의 존재와 새 Chat이 그 경로를 선택하는 것은 별개다.
검색 후 문서 선택·외부 사본 재사용·웹 도구 호출 선택의 불확실성은 남아 있으며, 이번 수정으로 해결됐다고 보고하지 않는다.

새 회귀의 RED를 클라우드에서 먼저 확인한 뒤 전체 CI와 Coverage100%, CodeQL 및 독립 코드 리뷰를 통과했다.
병합6d50cb3의 CI41390895569·Coverage41390895595·CodeQL41390895586·배포41390895571도 통과했다.
로컬 자원 보호가 테스트 실행을 거절해 우회하지 않았고 브라우저와 전체 테스트를 겹치지 않았다.
소유 임시 대화·캡처·세션만 finally에서 회수하고 사용자 Chrome과 다른 작업 세션은 유지했다.
공개 MCP10도구, JSON API, CLI, 기존 캐시·한도·인증 계약은 바꾸지 않았다.
