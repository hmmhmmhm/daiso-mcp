# 올리브영 HTTP 중계

브라우저를 실행하지 않고 맥에서 공식 조회 API를 호출하는 선택 모드입니다. 기존 REST/MCP/CLI와 중계 인증·캐시·호출 한도·원장을 유지합니다. 맥의 전원·네트워크·중계 프로세스는 계속 필요합니다. 기존 GUI LaunchAgent의 로그인 시작 조건까지 변경하는 기능은 아닙니다.

## 실행 설정

Python3 표준 라이브러리만 사용하며 별도 pip 패키지나 쿠키 파일은 필요하지 않습니다. 아래 두 값을 기존 비공개 relay.env에 추가합니다.

```sh
OY_RELAY_TRANSPORT=http
OY_HTTP_PYTHON=/opt/homebrew/bin/python3
```

Python 경로는 설치 환경에 맞춥니다. 설정을 생략하면 기존 browser 모드이며, http 모드가 실패해도 자동으로 브라우저를 띄우지 않습니다. 운영 토큰이나 개인 프로필은 Python 프로세스에 전달하지 않습니다.

## 확인할 기능

- 상품 검색: product-search-v3
- 매장 검색: find-store
- 상품 식별자 조회: stock-goods-info-v3
- 매장별 재고: stock-stores

중계 health에서 `transport: http`, `browserRequired: false`, `pages: 0`, `state: ready`를 확인합니다. ready는 실행 준비 상태이며 공식 서비스의 모든 요청 성공을 보장하는 표시는 아닙니다. 실제 상품·매장·재고도 함께 검증해야 합니다.

고정 공식 주소와 네 경로만 허용합니다. 리다이렉트, HTTP200이 아닌 응답, 잘못된 JSON/성공 형식, 응답 용량 초과 및 시간 초과는 실패로 반환합니다. 차단 HTML을 재고0으로 바꾸지 않습니다. 네트워크 읽기15초, 자식 프로세스18초, 응답2MiB 상한이며 별도 외부 요청 재시도는 하지 않습니다.

## 전환·되돌리기

원장과 비밀 설정을 먼저 권한600인 비공개 위치에 백업합니다. 진행 요청이 없을 때 기존 중계를 정상 종료하고 소유 브라우저의 종료를 확인한 뒤 코드와 설정을 반영합니다. quota.json이나 인증 값을 초기화하지 않습니다.

HTTP 조회가 차단되면 원인을 확인하고 `OY_RELAY_TRANSPORT=browser`로 변경해 중계를 재시작할 수 있습니다. 브라우저 모드에는 기존 GUI 환경과 Playwright 설치가 필요합니다. 쿠키나 브라우저 인증을 HTTP 모드에 복사하여 재사용하지 않습니다.

## 2026-10-06 실측

같은 맥에서 쿠키 없는 Python urllib는 네 API의 HTTP200/SUCCESS를 반환했고 Node fetch·Node https·기본 curl은 403을 받았습니다. Python도 필수 헤더를 제거하면403이었습니다. JSON 공백/문자 인코딩 변경은 원인이 아니었으며 정확한 차단 기준을 TLS만으로 확정하지 않습니다.

브라우저 중계와 동일 조건에서 상품 코드·상세 식별자·매장 코드·실제 재고 필드를 대조했습니다. 명동2가점 핸드크림 일반9/오늘드림7, 선크림 일반54/오늘드림43 및 픽업/취급 상태가 일치했습니다. 이 수량은 확인 당시 관측값이며 이후 변할 수 있습니다. HTTP 성공 여부는 제공자 정책·네트워크·클라이언트 버전에 따라 달라질 수 있으므로 장기간 무차단을 보장하지 않습니다.

## 2026-10-11 장애 확인

운영 health의 `ready`는 Python 실행 가능 여부만 확인합니다. 같은 고정 헤더와 공식 `product-search-v3` 요청이 HTTP403/HTML을 반환하면 상품·재고 조회는 중계502가 됩니다. 이번 확인에서는 설치된 Python 헬퍼의 요청도403을 받았으며, 설정·JSON 스키마 오류를 나타내는 근거는 없었습니다. 로컬에 기록된 네 공식 경로 이외의 대체 공개 API는 확인하지 못했습니다. 차단 기준이나 변경 시점은 이 응답만으로 확정할 수 없습니다.

HTTP 모드의 health에 `lastFailure: { status, at }`가 추가됩니다. `status`는 헬퍼가 받은 원래 HTTP 상태 숫자이며, 네트워크·프로세스·직렬화 실패 등 상태를 알 수 없는 경우 `null`입니다. `at`는 실패를 관측한 UTC 시각입니다. 다음 요청을 시작하거나 성공하면 이전 실패 정보는 지워집니다. 상위 응답 본문·URL·쿠키·토큰은 포함하지 않습니다. 외부 오류 응답과 요청 허용 경로,15/18초 제한,2MiB 상한은 유지합니다.

기존 소유 브라우저를 임시 독립 세션으로 실행한 정상 페이지 이동 후 네 공식 조회(매장9개·상품 검색·상품 식별자·매장 재고)는 모두 `SUCCESS`를 반환했고 감시 프로세스의 종료도 확인했습니다. HTTP 실패를 헤더 변형·쿠키 복사·보안 검증 자동화로 회피하지 않습니다. browser 모드 복구는 명시적 설정 변경으로만 수행하며, 브라우저 없는 실행이 필요하면 현재 HTTP403 차단이 해소되거나 제공자가 지원하는 다른 접근 경로가 필요합니다. 이 검증 자체는 운영 설정이나 원장을 수정하지 않았습니다.

인증된 운영 점검의 `x-health-check-force-fresh: true`는 상품·매장 fallback과 상품 식별자 캐시를 우회하고, 재고 보강 오류를 그대로 보고합니다. 릴레이에 `x-relay-cache-bypass: true`를 전달하여 저장 응답과 진행 중인 동일 요청도 재사용하지 않습니다. 이때도 인증·호출 한도·동시 작업 상한을 적용합니다. 인증되지 않은 공개 요청은 이 우회를 사용할 수 없습니다.

## 브라우저 감시자 비정상 종료 후 복구

브라우저 모드에서 감시자가 비정상 종료하면 새 브라우저를 즉시 실행하지 않습니다. 준비 완료 때 확보한 감시자 PID, 브라우저 PID·프로세스 그룹·생성 시각·전용 crashpad 경로와 마커를 대조합니다. 감시자가 숫자형 비정상 종료 코드로 끝났고 해당 PID·그룹·crashpad 프로세스가 모두 사라진 경우에만, 현재 사용자 소유의 일반 마커 파일을 `.exited-...` 이름으로 보존 이동합니다. 파일 교체·심볼릭 링크·큰 본문·소유권 불일치·조회 기한 초과가 있으면 기존 실패를 유지합니다. 시작 전 실패나 종료되지 않은 감시자, 시그널 종료도 자동 복구하지 않습니다.

이 확인은 기존 종료 기한 안에서 한 번만 공유합니다. 확인이 끝나면 다음 요청에서 새 브라우저를 준비할 수 있지만, 처음 실패한 원본 요청을 성공으로 바꾸거나 자동으로 무한 재시도하지 않습니다. 인증 자료와 누적 호출 원장은 수정하지 않으며, 원본의 간헐적 차단·지연을 해소한다는 의미도 아닙니다.

이미 실패 상태로 남은 구버전 프로세스는 먼저 유휴 상태를 확인해 정상 종료합니다. 남은 마커의 감시자 PID·브라우저 PID·원래 그룹·전용 crashpad 프로세스가 모두 없는지 확인한 뒤 마커를 보존 이동하고 LaunchAgent를 다시 시작합니다. 소유권이 불명확하면 다른 브라우저를 종료하거나 마커를 삭제하지 않습니다. 복구 후 캐시 우회 실제 조회와 CLI/MCP, 정기 경로 스냅샷을 확인합니다.


## 2026-10-25 반복 종료 장애와 상시 복구

일반 HTTP 중계는 현재도 공식 상품 검색에서 HTTP403을 반환했습니다. 별도 격리 Chrome의 headless 실행도 공식 메인 페이지와 상품 API에서403이 확인됐습니다. 창 없는 실행이나 HTTP 전환이 검증되기 전에는 정상인 browser 모드를 유지합니다. Chrome 창을 닫으면 해당 세션의 조회에 영향을 줄 수 있습니다. 개인 Chrome 프로필이나 쿠키는 사용하지 않습니다.

브라우저 교체 시 종료 확인이 제한 시간을 넘기면 원래 요청은 실패로 남깁니다. 이후 감시자의 정상 종료가 확인됐거나, 숫자형 비정상 종료 후 기존 PID·그룹·전용 crashpad 및 마커의 소멸/동일성 검증을 다시 통과한 경우에만 다음 작업에서 세션을 재생성합니다. 시그널 종료·살아 있는 감시자·불확실한 소유권은 계속 차단합니다. 원래 종료 기한을 늘리거나 재고0으로 대체하지 않습니다.

Mac 중계는 기존60초 heartbeat에서 로컬 수명 상태를 확인합니다. failed/idle이고 작업 중이 아닐 때만 준비를 시도하며 동시 시도를 공유합니다. 실패하면1분,2분,4분,8분,최대15분 간격으로 대기합니다. 이 감시는 상품·재고 API를 호출하지 않으며, Worker의5분 경로 선택 및 GitHub 원본 조회 검사를 대체하지 않습니다. 실제 복구 뒤 운영 fresh 조회와 CLI/MCP 검증은 별도로 필요합니다. 로그는 recovery-started/recovery-ready/recovery-failed/cleanup-recovered 같은 고정된 사유만 남기고 인증/오류 원문을 저장하지 않습니다.

일반 사용자 요청과 자동 준비도 같은 수명 계층의 실패 대기(retryAt)를 적용합니다. 요청을 반복해도 대기를 연장하거나 우회하지 않습니다. 부모 프로세스가 재시작되어 메모리 기록이 없는 경우에는 private 마커의 정수형PID·부모PID·그룹·생성시각·전용crashpad 형식과 파일 소유자·inode/device를 확인하고, 현재 관련 프로세스가 모두 없을 때만 원본 기록을 보존 이동합니다. 시작 중 기록처럼 브라우저 정체가 없는 마커는 계속 차단합니다. 이 복구에서는 프로세스를 추정해 종료하지 않습니다.

동시 재시작·종료 복구는 마커 경로의 SHA-256으로 정한 loopback TCP 포트(49152~65535)의 OS lease로 직렬화합니다. 시작 검증부터 감시자의 새 마커 획득까지와 후속 소멸 재검증/보존 이동에 같은 lease를 사용합니다. 임시 리스너는 외부 인터페이스에 노출하지 않고 연결을 즉시 닫습니다. 충돌·사용 중이면 소유권을 추정하지 않고 실패로 유지합니다. lease는 작업 완료 또는 부모 프로세스 종료 때 OS가 해제하므로 별도 stale lock 파일은 남기지 않습니다.
