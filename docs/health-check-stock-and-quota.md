# 실제 재고 점검과 중계 사용량 제한

전체 점검(`mode=full`)은 상품·매장 조회와 실제 재고 조회를 함께 확인합니다. 빠른 점검(`mode=quick`) 성공만으로 전체 재고 기능의 정상 동작을 판단하지 않습니다.

- CU: 강남역 주변 매장 1곳의 `stock` 수량을 확인합니다.
- GS25: `storeLimit=1`로 조회하고 `realStockQuantity`를 확인합니다.
- 세븐일레븐: `storeLimit=1`로 핫식스 단일 매장 재고를 확인합니다. 일반 검색어 ‘커피’의 첫 상품은 재고 조회 대상이 아닌 커피캔디일 수 있으므로 점검 상품으로 사용하지 않습니다.
- 올리브영: `stockCheckLimit=1`로 실제 매장 재고를 확인합니다. 상품 검색 결과만 있거나 `unknown` 상태이면 정상으로 판정하지 않습니다.

확인된 수량 0은 품절입니다. 미확인 값·음수·상품 목록만 있는 응답은 정상 재고 응답과 구분합니다. 재고 증거가 없는 결과는 `fail`로 보고하며, 원본 응답과 진단은 점검 기록에 남깁니다.

## 429의 출처

CU·GS25·세븐일레븐 Mac 중계는 같은 원장을 공유하며 분당 69회, UTC 하루 100,000회로 제한합니다. Cloudflare 직접 경로의 호출과 별개입니다. 분당 상한에 도달해도 일일 상한에 도달했다는 의미는 아닙니다.

응답의 `diagnostics.quotaReason`이 `minute`, `daily`, `consumer`, `consumer-busy`이면 중계가 확인한 자체 정책 제한입니다. `retryAfter`는 재시도까지 기다릴 초 단위 시간입니다. 단순 HTTP 429만으로 자체 제한과 원본 업체 제한을 구분하지 않습니다.

헬스체크 결과에도 `errorCode`, `upstreamStatus`, `quotaReason`, `retryAfter`를 보존합니다. Actions는 실패 직후 전체 점검을 다시 실행하지 않습니다. 정상 경로까지 반복 호출하며 중계 한도를 소비하던 동작을 제거했습니다. 첫 실패 기록을 보존하고 다음 점검에서 재확인합니다.

CGV·디트릭스 중계는 기존 디트릭스 원장을 공유합니다. 편의점 원장과 분리되어 있으며 이번 복구로 한도를 늘리거나 원장을 초기화하지 않습니다.
