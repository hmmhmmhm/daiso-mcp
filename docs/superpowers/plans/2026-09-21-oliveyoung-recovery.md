# 올리브영 직접 요청 복구 계획

## 조사

2026-09-21 임시 Cloudflare 원격 Worker에서 인증 없는 상품 검색을 비교했다.
기존 헤더는 반복한 세 요청 모두 403이었다. 데스크톱 User-Agent만 추가한 경우
200과 403이 섞였다. User-Agent, Origin, Referer, Accept-Language 조합은
최초 403 관측 후 연속 세 번 200/SUCCESS였으며 선크림 399개 중 실제 상품
`A000000263510`이 반환됐다. 개별 헤더를 제거한 실험도 결과가 변동하므로
특정 헤더 하나가 유일한 원인이라고 단정하지 않는다.

기존 앱의 원격 프리뷰 `/api/oliveyoung/products?keyword=선크림&limit=1`도
수정 전 직접 요청 실패를 반환했다.

## 구현 및 검증 순서

1. 직접 요청에 확인한 헤더 조합을 기대하는 회귀 테스트를 추가하고 실패를 확인한다.
2. 릴레이를 설정하지 않은 직접 요청에만 고정 헤더를 추가한다.
3. 릴레이 URL 우선순위, 토큰 전달 범위, 리다이렉트 거부와 재시도 금지를 유지한다.
4. 원격 프리뷰에서 상품·매장·재고 API를 확인한다. 응답 변동 및 캐시 제약을 기록한다.
5. 서비스 테스트와 릴레이 보안 회귀 테스트를 실행한다. 운영 배포는 하지 않는다.

## 구현 및 실제 결과

- 별도 원격 fetch 비교에서 `redirect: 'error'`는 Workers가 지원하지 않아
  `Invalid redirect value ... follow or manual` TypeError를 발생시키는 것을 확인했다.
- 해당 런타임 동작을 재현하는 실패 테스트를 작성한 뒤 `redirect: 'manual'`로
  변경했다. 기존 `expectedStatus: 200` 검사로 3xx를 거절하며 리다이렉트를 따라가지 않는다.
- 실제 전송 모듈을 임시 원격 Worker에 직접 import해 앱 캐시 없이 비교했다.
  manual 모드만 적용하고 추가 헤더를 제거하면 네 API 모두 403이었다.
  고정 헤더 조합을 복구하면 상품 검색 SUCCESS/399개, 매장 검색 SUCCESS/50개가
  확인됐지만, 동일 조합에서도 간헐적인 403은 남았다.
- `stock-stores`: 실제 상품 ID `8809962545756`의 50개 매장 응답 확인.
  서래마을점 응답에는 remainQuantity 19, o2oRemainQuantity 15가 있었다.
- `stock-goods-info-v3`: 상품 번호 `A000000263510`의 반복 조회는 403이었다.
  따라서 상품별 근처 매장 재고 흐름의 완전한 복구를 확인하지 못했다.
- 전체 앱 원격 프리뷰는 상품/매장 HTTP 200을 반환했다. 재고 API도 후속 호출에서
  HTTP 200이었지만 `stockCheckedCount: 0`, `stockUncheckedCount: 1`,
  `stockSource: global_search`였으므로 상세 재고 복구 증거로 보지 않는다.
- 외부 403 변동에 대응하는 추가 재시도나 캐시 확대는 하지 않았다. 설정된 릴레이
  우선순위와 토큰 범위는 유지한다. 브라우저 호스트가 불필요하다고 결론 내리지 않는다.
- 최종 검증: 올리브영 서비스/API 핸들러/앱 라우트 테스트 9개 파일, 93개 통과.
  실제 로컬 HTTP 서버를 이용한 릴레이 리다이렉트 비밀 미전달 검사도 포함한다.
  변경한 TypeScript 파일의 ESLint 및 전체 `tsc --noEmit` 통과.
