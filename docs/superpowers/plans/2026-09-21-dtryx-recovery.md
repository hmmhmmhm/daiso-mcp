# Dtryx 복구 조사 — 2026-09-21

## 목표와 범위

#187의 배포 Worker 시간 초과를 재현하고, 전송 경로와 클라이언트 제한 시간 처리를 구분한다. 근거가 확인된 변경만 구현하고 먼저 실패하는 회귀 테스트를 작성한다. 서비스 소스·테스트와 이 조사 기록만 수정하며 커밋·배포·유료 API 호출은 하지 않는다.

## 조사 순서

1. #187, #188, #190 및 클라이언트의 호출·본문 읽기·취소 경로를 확인한다.
2. 동일 극장과 엔드포인트로 로컬 30443/443, 배포 Worker를 제한된 횟수로 비교한다.
3. 가능하면 임시 원격 Worker에서 네트워크 단계별 진단을 비교한다.
4. 원인이 확인되면 최소 변경을 TDD로 구현한다. 확인되지 않으면 미해결 조건과 후속 진단을 명시한다.

## 확인된 사실

- [#187](https://github.com/hmmhmmhm/daiso-mcp/issues/187): 같은 단일 극장이 성공과 실패를 반복하며 배포 경로의 상영작 조회 오류는 시간 초과다. 전 극장 실패를 성공 200으로 바꾸면 실제 실패를 가릴 수 있다.
- [#188](https://github.com/hmmhmmhm/daiso-mcp/pull/188): 443으로 바꾸자는 제안이며 작성자도 Worker 복구 효과는 검증하지 못했다고 명시했다.
- [#190](https://github.com/hmmhmmhm/daiso-mcp/pull/190): 동일 조건의 443 Worker 시험 두 번 모두 시간 초과였으므로 #188을 포함하지 않았다.
- 클라이언트는 요청당 AbortController를 만들고 `response.json()`까지 기다린 다음 `finally`에서 타이머를 해제한다. 따라서 헤더를 받자마자 제한 시간이 사라지는 결함은 없다. 기본값은 15초이며 재시도는 없다.
- `includePlayDates`의 두 요청과 여러 극장의 요청은 병렬 실행한다. 한 극장 상영작 호출만으로도 문제가 발생하므로 다중 극장 동시성만으로 설명되지 않는다.
- [Cloudflare 공식 문서](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#allow-specifying-a-custom-port-when-making-a-subrequest-with-the-fetch-api)는 2024-09-02부터 `allow_custom_ports`가 기본이라고 설명한다. Cloudflare 프록시를 쓰지 않는 호스트에는 임의 포트가 허용된다. 따라서 일반적인 Cloudflare 프록시 지원 포트 표만으로 30443 차단을 단정할 수 없다.

## 실측

2026-09-21, Windows 로컬 Node fetch에서 각 회차마다 아래 세 경로를 동시에 호출하고 세 회차는 순서대로 실행했다. 대상은 `spacedog / 000072`, `third-party-type2-movie-now`이며 클라이언트 외부 제한은 8초다. 배포 API에는 `timeoutMs=5000`을 전달했다.

| --- | ---: | ---: | ---: | --- |
| api.dtryx.com:30443 | 415 | 248 | 280 | 3/3 HTTP 200, success, 34건 |
| api.dtryx.com:443 | 281 | 232 | 247 | 3/3 HTTP 200, success, 34건 |
| mcp.aka.page/api/dtryx/movies | 5658 | 5287 | 5392 | 0/3, HTTP 500 DTRYX_NOW_SHOWING_FAILED, 디트릭스 API 호출 시간 초과 |

로컬 DNS는 A `222.234.220.30` 한 개를 반환했으며 AAAA 주소는 반환하지 않았다. 별도 curl 실측도 두 포트 HTTP 200이었다.

| 포트 | TCP 연결(s) | TLS 완료(s) | 첫 바이트(s) | 전체(s) |

## 현재 판단과 제한

로컬 원본 API는 응답하지만 배포 경로에서 제한 시간이 소진되는 현상까지 확인했다. DNS, TCP, TLS, HTTP 헤더, 본문 중 Worker의 어느 단계가 멈추는지는 아직 알 수 없다. 포트 변경과 재시도가 문제를 해결한다는 근거는 없다. 임의의 포트 교체나 기본 시간 증가, 전체 실패의 성공 응답 변환은 적용하지 않는다.

임시 원격 Worker 진단 결과는 후속 기록한다. 로컬 단위 테스트 통과는 배포 전송 경로 복구를 증명하지 않는다.

## 원격 Worker 비교 결과

부모 작업에서 `wrangler dev --remote`로 띄운 임시 전체 앱(`127.0.0.1:8789`로 전달, 프로덕션 변경 없음)을 사용했다. 동일 상영작 요청, `timeoutMs=5000`, 외부 제한 10초를 유지했다.

| 임시 원격 Worker 원본 포트 | 1회(ms) | 2회(ms) | 결과 |
| --- | ---: | ---: | --- |
| 현재 30443 | 6095 | 5163 | 0/2, HTTP 500 시간 초과 |
| 일시 교체한 443 | 5603 | 5181 | 0/2, HTTP 500 시간 초과 |

443 변경은 되돌렸다. 이 실험은 #190의 결과를 다시 관측했으며, 포트 변경을 복구책으로 채택할 근거를 얻지 못했다. 이어서 fetch 시작과 헤더 도착에만 임시 로그를 넣은 한 번의 요청도 5696ms 후 시간 초과였다. 진단 로그는 실행 후 제거했다.

`git diff -- src/services/dtryx`는 비어 있고, `npm test -- tests/services/dtryx`는 6개 파일 94개 테스트가 통과했다. 동작 변경을 남기지 않았으므로 새 회귀 테스트를 추가하지 않았다. 복구 여부는 미해결이며 이슈를 닫을 수 없다.

## 다음 진단의 완료 조건

- Worker의 fetch 시작과 응답 헤더 수신 사이에서 멈추는지 로그로 확인한다.
- 헤더 이전 실패라면 업스트림 운영자의 TCP/TLS 또는 접근 로그와 요청 시각을 대조해야 DNS·라우팅·방화벽·TLS 중 원인을 구분할 수 있다. 로컬 성공만으로 원본 서비스가 Cloudflare 송신 주소에도 정상 응답한다고 단정할 수 없다.
- 수정 후보가 있다면 같은 원격 Worker에서 원래 경로와 후보 경로를 비교하여 유효한 JSON 성공을 확인하고, 기존 15초 전체 제한과 실패 응답 의미를 유지하는 최소 변경을 테스트부터 작성한다.
- 재시도는 현재의 연속 실패 표본에서 효과가 입증되지 않았고 단순 15초 재시도는 최대 응답 시간을 늘린다. 효과와 전체 제한 시간을 함께 검증하기 전 기본 동작에 넣지 않는다.

## 추가 진단: 응답 헤더와 User-Agent

부모 작업이 원격 로그에서 `DTRYX_DIAGNOSTIC_FETCH_START`만 있고 `DTRYX_DIAGNOSTIC_HEADERS`는 없음을 확인했다. 해당 요청은 응답 본문이 아니라 응답 헤더 수신 전에 멈췄다.

다른 서비스에서 효과가 확인된 데스크톱 User-Agent만 임시로 추가해 비교했다. 최초 000072는 590ms에 200이 되었지만, 헤더를 제거한 같은 요청도 4회 연속 성공했다(242/549/105/97ms). 따라서 한 번의 성공만으로 User-Agent가 원인이라고 볼 수 없다.

추가 극장 000067/000069는 헤더 없이 각각 5618/5118ms 시간 초과였고, 헤더 추가 후 987/222ms에 성공했다. 캐시 영향을 구분하려고 User-Agent를 다시 제거하고 `cache: no-store`만 임시 적용했을 때 000072/000067은 성공했다(911/140ms). 새 극장 000065도 666ms에 성공했지만 000088은 5109ms 후 시간 초과였다. 즉 제한된 표본에서는 헤더 변경, 시간대별 간헐성, 연결/캐시 상태를 분리하지 못했다.

User-Agent와 no-store를 모두 원복했으며 서비스 소스의 최종 diff는 없다. 이 추가 실험도 영구 수정의 인과 근거로 사용하지 않는다. 원격 경로에서 성공과 헤더 이전 시간 초과가 모두 관측되므로 단순 포트 차단이나 항상 실패하는 URL 조립 결함으로 설명할 수 없다.

## 최종 통제 실험: 캐시와 재업로드 영향 제거

앞선 전체 앱 비교는 `src/api/routes/dtryxRoutes.ts`의 `withEdgeCache`가 성공한 전체 URL을 캐시한다는 교란 요인이 있었다. 요청의 `Cache-Control`이나 내부 fetch의 no-store만으로 바깥 캐시가 사라지지 않는다. 소스 파일 저장 직후 원격 Worker 업로드가 완료되기 전에 요청하면 이전 변형이 실행될 가능성도 있다. 따라서 앞선 User-Agent A/B에서 성공 후 원복 성공을 인과 판단에 사용하지 않는다.

이를 제거하려고 단일 임시 Worker 스크립트가 쿼리 `variant=original|ua`로 User-Agent 유무만 선택하게 했다. 30443, 극장 000072, WorkGuID, Accept는 동일하며 내부 `cache: no-store`, 5초 제한을 양쪽에 고정했다. 앱의 캐시 코드를 거치지 않고 매번 고유 `probe`도 추가했다. 실험 중 스크립트는 수정하지 않았다.

| 순서 | User-Agent | 결과 | 원본 요청 시간(ms) |
| --- | --- | --- | ---: |
| A1 | 없음 | HTTP 200, success, 34건 | 295 |
| B1 | 데스크톱 Chrome 153 | HTTP 200, success, 34건 | 77 |
| A2 | 없음 | HTTP 200, success, 34건 | 70 |
| B2 | 데스크톱 Chrome 153 | 헤더 수신 전 TimeoutError | 5000 |

**최종 판단:** User-Agent 없는 요청도 정상 응답하고 데스크톱 User-Agent 요청도 시간 초과된다. 따라서 CGV에서 효과가 확인된 User-Agent 수정을 Dtryx에 그대로 적용할 근거가 없다. 제한된 표본은 Worker 전송 경로의 간헐성을 보여주지만 네트워크 원인을 구분하지 못한다. 임시 서비스 소스 변경은 모두 제거했고 최종 산출물은 조사 기록이다. 업스트림 또는 Cloudflare 전송 로그와의 대조가 다음 진단 단계다.

## 재시도 완화 가능성 확인

원인을 해결하지 못하더라도 같은 요청의 두 번째 시도가 회복되는지 추가로 확인했다. 먼저 같은 원본 조건을 네 번 순차 실행했으나 모두 헤더 수신 전 5초 시간 초과였다.

이어 정적 임시 Worker의 `variant=retry`가 동일 요청 안에서 최대 두 번만 원본 GET을 실행하도록 했다. 각 시도는 5초, 합계 최대 10초이며 헤더 수신 후 오류는 재시도하지 않는다. 이 코드는 진단 전용이며 제품 소스에 추가하지 않았다. 세 번의 결과는 다음과 같다.

| 진단 요청 | 첫 시도 | 둘째 시도 | 총 시간 |
| --- | --- | --- | --- |
| 1 | 헤더 전 시간 초과 5000ms | 헤더 전 시간 초과 5000ms | 10000ms |
| 2 | 헤더 전 시간 초과 5000ms | 헤더 전 시간 초과 5000ms | 10000ms |
| 3 | HTTP 200, 34건, 97ms | 실행하지 않음 | 97ms |

이번 표본에는 첫 시도 실패가 다음 시도로 회복된 사례가 없었다. 제한 시간 일부를 잘라 재시도를 위한 예산을 확보하면 정상적으로 느린 응답까지 중단할 수 있으므로, 효과가 확인되지 않은 상태에서 기본 동작을 바꾸지 않는다. 향후 같은 요청에서 재시도 회복이 관측되면 원래 전체 제한 시간 안에서만 한 번 재시도하고, HTTP 오류·JSON 파싱·RetCode 오류는 그대로 보존하는 방안을 별도로 검증할 수 있다.
