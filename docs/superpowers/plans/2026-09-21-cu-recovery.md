# CU 매장 조회 복구 조사 및 구현 계획

## 범위

- `src/services/cu/**`, `tests/services/cu/**` 및 CU 조사 문서만 수정한다.
- 무료 공식 웹 조회를 조사한다. 유료 폴백이나 오류를 빈 성공으로 바꾸는 처리는 추가하지 않는다.

## 확인한 사실

2026-09-21 로컬 Node 환경에서 인증 없이 15초 제한으로 확인했다.

- 변경 전 `fetchCuStores({ searchWord: '강남' })`: 실제 매장 5개 반환.
- 공식 페이지 `https://cu.bgfretail.com/store/list.do?category=store`: HTTP 200.
- 공식 페이지의 `searchList(pageNo)`는 `type: "post"`, `/store/list_Ajax.do`, `$('#listForm').serialize()`를 사용한다.
- 공식 폼에는 현재 코드의 검색 필드와 빈 `user_id` 필드가 있다.
- 현재 클라이언트의 전체 헤더와 폼을 유지한 GET/POST 비교: 둘 다 HTTP 200, 동일 매장 코드 `39418`, `50212`, `48893`, `50615`, `51006` 반환.
- 따라서 GET이 공식 호출 방식이라는 기존 주석은 잘못되었지만, 메서드만으로 운영 HTTP 400의 원인이라고 결론 내릴 수 없다.
- 변경 전 CU 테스트: 4개 파일, 52개 테스트 통과.

## 다음 단계

1. Cloudflare 실행 환경에서 동일 GET/POST를 비교해 로컬 환경과의 차이를 확인한다.
2. 성공하는 요청 계약이 확인되면 해당 회귀 테스트를 먼저 작성하고 예상 실패를 확인한다.
3. 입증된 최소 수정만 적용하고 CU 테스트 및 실제 조회를 다시 실행한다.
4. 원격 환경에서도 모두 실패하면 메서드 변경을 복구로 주장하지 않고 제약과 증거를 기록한다.

## Cloudflare 원격 비교 결과

- 임시 `wrangler dev --remote` 프리뷰의 `/api/cu/stores?keyword=강남&limit=1`에서 변경 전 GET은 upstream HTTP 400을 반환했다.
- POST 계약 회귀 테스트를 먼저 수정하여 예상한 GET/POST 불일치 실패를 확인했다.
- 메서드와 폼 위치만 POST로 바꾼 임시 후보도 원격 요청 두 번 모두 같은 upstream HTTP 400을 반환했다.
- POST 복구 가설은 원격 비교에서 입증되지 않았다. 임시 소스와 테스트 변경은 모두 되돌렸다.
- 로컬에서 GET/POST가 모두 실제 매장을 반환하므로, 실행 환경에 따른 상위 서버 응답 차이가 남아 있다. 이것만으로 특정 차단 장비나 IP 정책을 확정할 수 없다.

## 원인 확인과 최종 수정

- 웹 전용 헤더에는 `User-Agent`가 명시되어 있지 않았다. Node와 Workers의 기본 헤더 차이를 가설로 세웠다.
- 헤더 계약 테스트에 `User-Agent: Mozilla/5.0` 기대값을 추가하고 기존 구현에서 실패함을 확인했다.
- 메서드는 기존 GET 그대로 두고 해당 헤더 하나만 추가했다. 원격 프리뷰가 HTTP 200과 실제 매장 5개로 바뀌었다.
- 헤더를 다시 제거하고 캐시를 피한 새 요청으로 upstream 400 재현을 확인했다.
- 헤더를 다시 추가한 새 요청은 다시 HTTP 200, 매장 코드 `39418`, 총 5개를 반환했다. 이 A/B/A 비교로 이번 원격 오류가 User-Agent 명시 여부에 달려 있음을 확인했다.
- 최종 수정은 웹 요청의 명시적 User-Agent와 회귀 테스트뿐이다. GET/POST 전환이나 재시도, 유료 폴백은 추가하지 않았다.
- 최종 CU 테스트: 4개 파일, 52개 통과. 프로덕션 배포는 수행하지 않았으며 운영 배포 후 동일 조회 확인이 필요하다.
