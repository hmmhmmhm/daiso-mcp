# 웹 읽기 세션 경로 실험 구현 계획

> 구현은 현재 세션에서 순서대로 수행합니다. 브라우저·테스트 병렬 실행을 하지 않습니다.

**목표:** 웹 도구가 기존 HTML 수집본을 재사용하는 상황에서 실제 링크 선택으로 새로운 응답 주소를 얻을 수 있는지 검증합니다.

**설계:** `/browse/read`는 임의 UUID를 포함한 `/browse/read/{id}/...` 링크를 제공합니다. 해당 경로는 같은 Worker의 기존 `/browse/...` GET으로만 전달하고 HTML의 내부 browse 링크를 세션 경로로 연결합니다. 새 응답 확인 링크는 새로운 UUID를 포함하면서 조회 조건을 유지합니다. API 캐시·권한·한도는 그대로 적용하며 원본 재고의 최신성을 보장한다는 표현은 사용하지 않습니다. JSON API와 공개 도구 10개는 바꾸지 않습니다.

**근거:** 2026-10-27 12:12 KST에 고정 상품 예제가 Crawled today이면서도 00:44 UTC 생성의 이전26.1 응답을 반환했습니다. /guide/latest는5일 전 redirect를 반환했습니다. 반면 새27.1 링크 입력 경로의 실제 click은 성공했습니다. UUID 경로가 이 현상을 피하는지는 미검증 가설입니다.

## 순서

- [x] `tests/pages/browseRead.test.ts`: 기존 등록 함수만 사용하여 루트 세션 링크·조건 보존·새 ID·중첩 거절·GET 제한의 기대 동작을 작성합니다. 아직 없는 경로의404가 기대200과 달라 실패하는지 확인합니다. 로컬 보호기가 Chrome3개 상태이므로 GitHub cloud CI에서 확인하고 실패를 정상으로 기록하지 않습니다.
- [x] `src/pages/browseRead.ts`: UUID 검증, 내부 browse만 전달, HTML 링크 및 Location 재작성, no-store/noindex, 새 응답 링크를 구현합니다. 외부 이미지·guide 링크는 그대로 유지합니다. 잘못된 ID·중첩 read 경로는 내부 호출 전400으로 거절합니다. 응답 실패 상태를 성공으로 바꾸지 않습니다.
- [x] `src/pages/browse.ts`: 기존 catchall보다 먼저 등록합니다. 쓰기·관리 API는 전달하지 않습니다.
- [x] Cloud CI에서 새 회귀와 전체 검사·커버리지를 통과시킵니다. 실제 배포 전에 독립 읽기 전용 리뷰를 수행합니다.
- [x] 배포 후 웹 도구의 실제 링크만으로 서로 다른 ID·응답 생성시각을 관측합니다. 고정 URL 결과와 비교합니다. 상품·매장·재고·진열 위치와 수량 미확인 구분을 유지합니다. 실제 Chat UI 검증은 브라우저 연결이 복구될 때 별도 수행합니다.
