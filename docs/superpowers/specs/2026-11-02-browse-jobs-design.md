# 느린 읽기의 접수·결과 전달

2026-11-02 사용자 승인과 별도 Worker 실험을 따른다. 실제 ChatGPT 새 임시 채팅2건에서5초 가상 작업의 접수→서로 다른 실제 결과 링크→ready 및 서버 requestId 일치를 확인했다. 같은 주소 재시도는 실패/과거 pending 재사용이 관측됐다.

- 우선 다이소 /browse/read 읽기 세션에만 적용하고 다른 서비스의 기존 경로는 유지한다. 실제 API 호출을 한 번 실행한다.1초 안에 끝나면 기존 응답을 반환한다. 느린 경우에만 별도 읽기 작업을 만들고 pending HTML 및 새 실제 결과 확인 링크를 반환한다.
- 원본 요청의 권한·IP별 한도·캐시를 기존 API에서 적용한다. 후속 상태 확인은 저장 결과만 읽고 원본을 다시 호출하지 않는다. 공개 MCP10도구/JSON/CLI와 일반 /browse 경로를 유지한다.
- 원본 호출과 HTML 장식을 waitUntil로 유지하고 사용자 연결 취소와 분리한다. 작업의25초 제한·5분 TTL·256KiB 저장 상한을 둔다. 제한·외부 오류·미확인 수량을 정상 재고0으로 바꾸지 않는다.
- 요청 헤더·인증·쿠키·원본 조회 조건은 작업 저장소에 보관하지 않는다. 안전한 공개 응답 본문·상태·Content-Type과 재시도·리디렉션·보안 헤더 허용 목록만 저장한다. 작업 주소는 무작위 UUID이며 상태 응답마다 다른 실제 후속 링크를 제공한다. HTML 생성·작업 완료·원본 재고 갱신 시각은 구별한다.
- 저장 실패 시 기존 동기 응답으로 복귀한다. 늦은 완료/알람의 경합으로 정상 결과를 덮어쓰지 않는다. 대기·만료는 HTML로 명확히 보고한다.
- 저장 및 순차 실제 API 경계를 가상시계로 검증하고, 필수 CI/Coverage100%/리뷰/배포 이후 실제 공개 조회와 ChatGPT 웹에서 상태 링크를 확인한다. 검증용 브라우저는 소유 창1개, 검사와 겹치지 않는다.
